# 0001. 전체 아키텍처

- 상태: 초안
- intent: intent/0001-sinclair-e2e-platform.md

## 레이어

1. **디바이스 레이어** (`packages/device-layer`): mobilecli 스타일 JSON-RPC 서버. Android는 접근성 헬퍼(artemis 방식, UiAutomation 비독점) + 입력 주입, iOS는 usbmux/go-ios 방식 + XCUITest 러너. 메서드 명명은 `device.io.tap`, `device.dump.ui` 계열. UI 트리는 `ScreenElement` + `@ref`.
2. **엔진** (`packages/engine-mobile`): 러너의 `Engine` 계약(observe/locate/perform + 선택 메서드) 구현. 구현한 메서드로 capability 결정. locator 해석의 모바일 세부(testId가 identifier/resourceId/Flutter key 매칭, bounds 기반 체이닝 fallback, 두 번 연속 같은 bounds일 때 actionable)는 mobilewright 참고.
3. **러너** (`packages/runner`): e2e 구조. 세 동사 분리(결정적 `screen` locator, 계획형 `agent.act`, 판정 `agent.assert/waitFor/extract`). 워커는 타깃당 1개, 실패 후 교체. 녹화 캐시는 검증 통과 후에만 기록, descriptor로 재탐색, 실패 시 스텝 중간부터 에이전트 이어받기, CI는 strict/read-only.
4. **에이전트**: 툴 루프 + artemis의 액션 전 안전망(XML 가중치 재탐색, 픽셀/VLM 비교), Incident 복구, Ledger 컨텍스트 관리. 닫힌 툴 스키마, secure 필드 redaction.
5. **백엔드** (`apps/control-plane`, `apps/runner-agent`): 아래 도메인 모델.
6. **프런트엔드** (`apps/studio`, `apps/console`, `packages/ui`).

## 백엔드 도메인 모델

Suite, TestCase(안정 ID), Cycle(빌드 + 기기 매트릭스 + Suite 필터), Run(Cycle × 타깃), Attempt(테스트 1건 시도; passed/failed/blocked/skipped + 에러 코드 + 캐시 결정), StepRecord, Artifact, Verdict, Issue(app-bug/test-bug/flaky/env, waive), Device(idle/leased/offline/untrusted), CacheEntry.

흐름: Cycle 생성 → Scheduler가 Run 생성·기기 lease → Runner Agent가 러너 실행, 커스텀 Reporter가 이벤트를 Ingest로 스트리밍(멱등) → 재시도 정책 → Cycle 종료 시 Verdict 계산·알림.

Run 클레임(최소 Scheduler, 2026-11-08 runner-agent 티켓 04): Run 은 `POST /cycles/:id/runs` 로 미리 등록되고, 에이전트가 `POST /runs/claim {targetId, agentId}` 로 "등록됐고 이벤트가 없으며 lease 가 없거나 만료된" Run 을 등록 순서로 하나 받는다(**Run lease**: `{agentId, expiresAt}`, TTL 기본 60초, `POST /runs/:id/heartbeat` 로 소유자만 연장, 에이전트는 TTL/3 마다). 이벤트가 하나라도 들어간 Run 은 에이전트가 죽어도 재클레임하지 않는다(부분 보고 run 의 재실행은 재시도 정책에서). 에이전트가 run 도중 lease 를 잃으면 heartbeat 를 멈추고 경고하되 run 은 끝까지 돌아 같은 runId 로 보고된다(러너는 테스트 중간 중단을 지원하지 않음; 알려진 한계). **기기 lease** 는 아래 "기기 lease" 절(device-fleet 02)에서 Run lease 에 실린다. Cycle 의 Suite 필터는 `suite: { tests, tags? }` 로 저장되며 에이전트는 `tests` 디렉터리를 쓴다(`tags` 는 저장만, 필터링은 후속).

Fleet 인벤토리(2026-11-08, device-fleet 티켓 01): 노드(데몬)가 `PUT /fleet/nodes/:agentId { devices[] }`(protocol `NodeReport`, 닫힌 검증기 `parseNodeReport`)로 꽂힌 기기 전체를 보고하고, 응답 `{ttlMs}` 의 1/3(하한 1초)마다 다시 보고한다. 노드 TTL 은 Run lease TTL 과 같다. `GET /fleet` 는 노드별 기기와 **기기 상태**를 조회 시점에 계산한다(저장하지 않음): 노드 보고가 TTL 을 넘기면 `offline`("노드 보고 끊김"), 보고에서 빠진 기기는 마지막 모습으로 남아 `offline`("보고에서 빠짐", 다시 보고되면 돌아온다), 아니면 미승인·adb offline·헬퍼 미준비·화면 잠김이 `untrusted`(사유), 나머지 `idle`. helper·locked 가 없으면(그 플랫폼에 개념이 없거나 확인 못 함) 막지 않는다. `leased` 는 기기 lease(02)부터. 보고 실패는 클레임을 막지 않는다. mobile 데몬은 디바이스 백엔드 하나를 소유해 인벤토리와 run 들이 같이 쓴다(직접 USB 는 한 프로세스만 잡을 수 있다; `run` 명령은 run 하나 동안만 연다). SQLite 는 스키마 3(`fleet_nodes`, NodeRecord JSON).

기기 lease(2026-11-08, device-fleet 티켓 02): 클레임 본문 `devices?: string[]`(노드의 후보 기기). control-plane 은 그중 다른 Run 이 쓰지 않는 첫 기기를 Run lease 에 `deviceId` 로 싣는다 — 기기 lease 는 Run lease 와 한 몸이라 heartbeat 가 함께 연장한다. 기기가 바쁜 조건은 파생된다: 그 기기를 가진 Run lease 가 만료 전이고, Run 이 대체되지 않았고, Run 이 끝나지 않았다(`run.finished` 가 들어오면 lease 만료를 기다리지 않고 풀린다; 취소도 run.finished 라 같다). 해제 엔드포인트는 없다. 빈 후보가 없으면 Run 을 주지 않는다(대기, `devices: []` 도 같다). SQLite 는 빈 기기 고르기와 Run 갱신을 한 트랜잭션(BEGIN IMMEDIATE)으로 해 두 핸들이 같은 기기를 두 Run 에 싣지 못한다. 기기 id 는 Fleet 전체에서 유일해야 한다(시리얼; fake 기기는 `fake-<agentId>`). `devices` 없이 클레임하는 구버전 에이전트는 기기 없는 lease 와 응답 `warning` 을 받는다(하위 호환). `GET /fleet` 는 lease 중인 idle 기기를 `leased`(+ `runId`)로, 잠김·뽑힘 같은 문제는 lease 중이어도 그 상태 그대로(+ `runId`) 보인다. Cycle 뷰는 `run.started.deviceId` 가 lease 된 기기와 다르면 `warnings`. 데몬은 마지막 인벤토리의 기기를 후보로 보내고 lease 받은 기기로 엔진을 만든다; 그 기기를 못 찾으면 blocked(infra-failed)로 보고되고 run 이 끝나 기기도 풀린다. 데몬이 `--device` 로 고정돼 있으면 그 기기만 후보로 낸다. 후보가 없으면 클레임하지 않고 한 번 알린다(mobile 데몬이 백엔드를 열지 못한 경우도 그렇고, 보고 때마다 다시 연다). 기기 상태로 후보를 거른다(device-fleet 05): "쓸 수 있는 기기" 규칙(`nodeDeviceProblem`: 미승인·adb offline·헬퍼 미준비·화면 잠김이면 사유)은 protocol 에 있어 노드(후보)와 control-plane(Fleet untrusted)이 같은 함수를 쓴다. 데몬은 타깃마다 클레임 직전에 인벤토리를 다시 읽어 쓸 수 있는 기기만 내고(뺀 기기는 사유가 바뀔 때만 로그; 읽기가 실패하면 그 차례는 클레임하지 않는다), 잠긴 mobile 기기는 빼기 전에 한 번 깨우고 화면 크기에 맞춰 위로 스와이프한다(비보안 잠금은 풀린다). 그래도 잠겨 있으면 보안 잠금으로 보고 화면을 다시 끄며, 풀린 것이 보이거나 기기가 빠졌다 다시 꽂힐 때까지 다시 깨우지 않는다(`apps/runner-agent/src/unlock.ts`; 잠긴 폰을 주기적으로 깨우면 화면이 거의 계속 켜진다). 보안 잠금 기기는 untrusted 로 남고 Run 은 blocked 로 끝나는 대신 다른 기기를 기다린다. 이 동작은 데몬 `--help` 와 설치본 README 에 운영자용으로 적혀 있다. run 이 끝나면(결과와 무관) 바로 다시 보고한다 — 보고 사슬은 언제나 하나(진행 중 보고를 기다린 뒤 새로 보고). 빠진 기기는 Fleet 에 offline(보고에서 빠짐)으로 곧 보인다. 알려진 한계: run 도중에는 그 기기의 잠금을 다시 보지 않으므로(run 을 방해하지 않게) run 도중 잠긴 것은 run 이 끝난 뒤 보고에서 드러난다. 서버는 후보를 다시 거르지 않는다(노드의 판단을 믿는다; 보고가 늦으면 멀쩡한 기기를 놓칠 수 있어서). 알려진 한계: Run lease 를 잃은 에이전트가 run 을 계속 돌리는 동안(현재 테스트를 마칠 때까지) 그 기기는 이미 풀려 다른 Run 에 lease 될 수 있다 — 대체된 Run 은 heartbeat 409 로 곧 취소되지만 그 짧은 창은 남는다. SQLite 는 busy timeout 2초.

타깃 = 기기 선택 조건(2026-11-08, device-fleet 티켓 03): Cycle 의 `targets` 원소는 이름 문자열(기존) 또는 조건 `{ id, platform, model?: 문자열|목록, osVersion?: { min?, max? } }`(protocol `TargetSelector`, 닫힌 검증기 `parseCycleTargets`, 매칭 `matchesTarget` — OS 버전은 점으로 나눈 숫자 비교, 숫자로 읽을 수 없는 기기 버전은 OS 조건에 맞지 않음). 한 Cycle 에 섞어도 된다. 같은 이름 문자열은 하나로 합치고 조건이 낀 같은 id 는 거부한다. 매트릭스 열은 타깃 id 이고 셀은 그 결과를 낸 Run 의 기기(`deviceId`)를 싣는다. 노드는 `targetId` 없이 `POST /runs/claim { agentId, devices, targets? }` 로 클레임하고, 서버가 등록 순서로 Run 을 고른다: 이름 타깃은 노드가 `targets`(데몬 `--targets`, 이제 선택)로 선언했을 때, 조건 타깃은 빈 후보 기기 중 조건에 맞는 것이 있을 때 — 기기 속성은 Fleet 보고에서 알며 보고하지 않은 기기는 조건 타깃을 받지 못한다. 맞는 빈 기기가 여럿이면 가장 오래전에 클레임된 기기(lease `claimedAt` 가 가장 이르거나 한 번도 안 쓴 기기 — 끝난 시각이 아니라 클레임 시각이다)를 준다 — 한 기기에 Run 이 몰리지 않게. 맞는 기기가 없으면 그 Run 은 건너뛰고(blocked 가 아니라 대기) 다음 Run 을 본다. Run 을 고르는 순서는 전역 등록 순서(FIFO)다: 이름 타깃을 여럿 선언한 노드는 앞 타깃의 밀린 Run 을 다 받은 뒤에 다음 타깃을 받는다 — 타깃별로 번갈아 주지 않는 것은 의도한 트레이드오프다(오래된 Cycle 의 일이 먼저 끝난다; 타깃 공정성이 필요하면 노드를 나눈다). 데몬은 폴링마다 클레임 한 번(예전에는 선언한 타깃마다 한 번)이고, `targetId` 없는 클레임을 모르는 구버전 control-plane 이 400 을 주면 이름 타깃마다 청하는 예전 방식으로 바꾼다. 클레임은 "이벤트가 있는 Run" 을 이벤트 저장소의 인덱스 조회(`hasEvents`)로 거른다(끝난 Run 이력 전체를 매 폴링 읽지 않게). 보고가 끊긴 노드의 기기 속성은 조건 매칭에 쓰지 않는다. `targetId` 를 주는 기존 클레임은 그대로이되 조건 타깃이면 기기가 맞아야 한다. 대체 Run 은 같은 targetId 라 같은 조건으로 다른 기기에서 돌 수 있다.

워커 프로세스와 다기기 데몬(2026-11-08, device-fleet 티켓 04): 러너의 테스트 등록이 프로세스 전역이라 한 프로세스에서는 run 이 하나씩만 돈다. bin 으로 띄운 데몬은 run 마다 같은 bin 을 숨은 명령 `__worker` 로 띄워 IPC(start/cancel → log/done)로 맡긴다(`apps/runner-agent/src/worker.ts`); 워커는 기존 `executeRun` 을 그대로 돌리고 스풀도 직접 쓴다. USB 는 데몬만 잡는다: 데몬이 디바이스 레이어를 127.0.0.1 HTTP JSON-RPC(토큰, 기기별 호출 직렬화는 같은 디스패처라 그대로)로 열고, 워커는 lease 받은 기기를 그것으로만 조작한다. 기기 준비(목록·헬퍼·깨우기·잠금·예열)와 정리(앱 종료·홈)는 데몬이 워커 전후로 한다(`AndroidNode.prepare/cleanup/serveRpc`); 준비가 실패하면 테스트 없이 blocked 로 보고한다. 데몬은 기기마다 한 번에 run 하나, 상한 `--concurrency`(기본 = 쓸 수 있는 기기 수)로 빈 기기만 후보로 클레임하고 run 을 기다리지 않고 다음 클레임을 한다(run 이 끝나면 바로 다시 본다). heartbeat 는 run 별로 데몬에서. 종료 신호는 모든 워커에 cancel 로 전파된다(각자 현재 테스트까지 마치고 cancelled). 워커는 터미널 신호를 무시하고 cancel 로만 멈춘다. 데몬이 죽으면(IPC 끊김) 워커도 곧바로 끝나 run 은 `run.finished` 없이 남고 재시도 정책의 버려진 Run → 대체 경로를 탄다(현재 테스트를 마치고 cancelled 로 보고하면 대체되지 않으므로). 워커가 결과 없이 죽으면 그 run 의 코드는 4(incomplete)이고 같은 규칙으로 정리된다. 워커가 30초 안에 start 를 못 받으면 끝나고, done 을 보낸 뒤에는 스스로 끝난다(데몬은 done 뒤 5초 안에 안 끝나면 강제 종료). 워커를 띄우지 못하면(실행 파일 없음 등) 그 run 은 4 로 끝나 버려진 Run 규칙을 탄다. 디버거 플래그는 워커에 넘기지 않는다. 워커 명령은 데몬이 자기 node·execArgv·bin 으로 만든다 — 리포 체크아웃의 bin 재실행 셸은 IPC 를 손자에게 전달하지 않으므로 변환 플래그가 이미 붙은 명령이어야 한다. 라이브러리로 부른 `runDaemon`(workerCommand 없음)은 예전처럼 같은 프로세스에서 하나씩.

Fleet 종단 증명(2026-11-08, device-fleet 티켓 06): `verify-runner-agent/scripts/fleet-e2e.sh` 가 실제 bin 데몬 두 개(가짜 기기는 `--fake-devices`, fake 엔진 전용·protocol 보고 검증기로 검사)로 조건 타깃 Cycle 을 동시에 채우고(잠긴 기기 제외), 노드 사망 시 다른 노드의 맞는 기기로 대체되는 것을 11개 판정으로 보인다. 실기기 노드와 가짜 노드가 한 Cycle 의 두 열을 채우는 것은 `fleet-e2e.device.test.ts`.

에이전트 골격(2026-11-08, agent-layer 티켓 01, `packages/agent`): 닫힌 툴 다섯(`tap(ref)`·`type(ref, text)`·`scroll(ref, up|down)`·`back()`·`done(summary)`)은 하나의 action spec 에 설명·인자·엔진 실행이 함께 있고, 모델용 JSON 스키마(추가 속성 금지·모든 인자 필수)와 실행 전 검사기가 그 표에서 나온다(계약 테스트). `runAct(engine, 목표, { executor, maxTurns=20, timeoutMs=120s })` 는 매 턴 secure 를 가린 트리를 한 줄에 노드 하나(`@ref role "이름"`)로 그려 `StepExecutor.next({ goal, observation, history, tools })` 에 묻고, 검사를 통과한 호출만 엔진에 실행한다. 검사 실패(rejected)와 엔진 오류(error)는 실행하지 않거나 실패한 채로 다음 턴 기록에 실어 모델이 고치게 하고 턴에 센다. `done` 이면 성공, 턴·시간 한도·실행기 예외면 실패(사유). 러너 fixture `agent.act(목표)` 는 실행기를 `runTests({ agent: { executor } })` 로 받고(없으면 설정 오류), act 하나가 `step.recorded(kind act, modelCalls)` 하나이며 instruction 에는 툴 이름과 ref 만 남긴다(입력한 글자는 비밀값일 수 있어 남기지 않는다). 실패는 errorCode `agent` 의 failed Attempt + 아티팩트. 테스트용 실행기는 대본(`scriptedExecutor`); 실제 모델은 02.

판정 동사(2026-11-08, agent-layer 티켓 03): `agent.assert(문장)`·`agent.waitFor(조건, {timeoutMs=30s, intervalMs=1s})`·`agent.extract(설명, 타입)` 은 화면을 바꾸지 않는다. 엔진은 관찰만 하고 모델에는 툴을 주지 않으며, 실행기의 선택 메서드 `judge({kind, question, observation, schema})` 가 닫힌 답 스키마(assert `{pass, reason}`, extract `{found, value, sourceRefs, reason}`)로만 답하고 에이전트가 같은 스키마로 다시 검사한다(Claude 는 구조화 출력 `output_config.format: json_schema`). waitFor 는 화면(그린 트리)이 지난번 거짓 판정 때와 같으면 모델을 다시 부르지 않는다. extract 타입은 string·number·boolean·`{키: 그 셋}` 이고 반환 타입이 추론된다. 근거 ref 가 secure 노드면 `secure-read`, 화면에 없는 ref·빈 근거·타입 불일치는 invalid. 러너: 판정 하나가 스텝 하나(kind assert/waitFor/extract, modelCalls·usage, instruction 에는 질문·판정·근거만 — 추출한 값은 남기지 않음). 거짓·기한 초과·못 찾음은 errorCode `assertion`(failed + 아티팩트), invalid 는 `agent`, judge 없는 실행기는 `agent-config`(blocked). 판정은 캐시하지 않는다.

Verdict 세부(2026-11-07, control-plane-ingest 티켓 05, `apps/control-plane/src/verdict.ts`): 마지막 Attempt 는 `attemptNo` 최대(끝난 것만). 케이스 집합은 Cycle 의 run 들이 본 testId 합집합. 어떤 타깃의 run 에 없는 케이스는 그 run 이 `infra-failed`/`cancelled` 면 `blocked`, `finished` 면 `skipped`. 태그는 TestCase 레지스트리가 생기기 전까지 테스트 이름의 `@태그` 토큰(e2e/Playwright 관례)이고 `requiredTags` 가 비면 모든 케이스가 필수. Cycle 상태는 run 없음 `draft`, 미종료 run 있음 `running`, 전부 종료 `finished`. Cycle Verdict 는 미종료면 `incomplete`, 모든 Run 이 `finished` 로 끝나고 필수 케이스 × 모든 타깃이 passed/passed-flaky/waived 면 `verified`, 아니면 `blocked`(infra-failed/cancelled Run 이 하나라도 있으면 케이스를 몰라도 blocked). 같은 타깃에 Run 이 여럿이면 뒤에 등록된 Run 의 결과가 앞을 덮는다(재실행). Verdict 는 저장하지 않고 조회마다 다시 계산한다(늦게 도착한 이벤트가 반영된다); 대신 끝난 Cycle 에는 Run 을 더 등록할 수 없다(409). `run.started` 에는 러너를 돌린 노드의 `agentId`(선택)가 실린다. `run.started` 의 cycleId/targetId 가 등록과 다르면 판정은 등록을 따르고 조회 응답의 `warnings` 로 드러낸다. Cycle 상태 `expired`/`cancelled` 는 Scheduler 가 생기기 전까지 쓰이지 않고(Run 상태 `cancelled` 는 러너 취소 신호가 만든다), `waived` 는 Issue/waive 가 생기기 전까지 생성되지 않는다. Cycle 과 Run 등록은 이벤트가 아닌 레코드(`CycleStore`)로 저장한다. 

재시도 정책 — 취소 신호(2026-11-08, retry-policy 티켓 02): `runTests` 옵션 `signal`(AbortSignal). abort 되면 진행 중 테스트는 끝까지 간다(러너는 테스트 중간 중단을 지원하지 않는다 — 명시된 한계). 그 테스트의 남은 재시도는 시작하지 않고(결과는 마지막 시도의 failed 그대로), 다음 테스트들은 `attempt.started/finished(skipped, errorCode cancelled)` 로 기록한다. 실제로 못 돌린 테스트나 재시도가 있을 때만 run 이 `run.finished state=cancelled` 로 끝난다(infra-failed 보다 우선) — 마지막 테스트 도중 신호가 와서 전부 돌았다면 `finished` 다. 리포트는 `cancelled: { reason }`(signal.reason). runner-agent 의 run 별 코드 `5 cancelled`(실패·blocked 보다 우선: 보고가 불완전하다는 뜻이 먼저다). 데몬 프로세스 종료 코드는 cancelled run 을 실패로 세지 않는다(그 몫은 Cycle 뷰가 blocked·대체로 드러낸다). 데몬은 run 마다 AbortController 를 만들어 heartbeat `not-owner`/`no-run`("lease 를 잃음")과 데몬 종료 신호 SIGTERM/SIGINT("종료 신호")를 같은 길로 러너에 전파한다 — 그래서 두 에이전트가 같은 Run 에 보고하는 창은 "현재 테스트 하나" 로 줄고, SIGTERM 도 run 전체가 아니라 테스트 하나 뒤에 멈춘다. 로그 "lease 를 잃어 중단", `DaemonSummary.runs[].cancelled` 에 사유. Verdict: errorCode `cancelled` 인 skipped 케이스는 "안 돌기로 한 것" 이 아니라 "돌지 못한 것" 이라 `blocked` 로 보이고(작성자의 `test.skip` 은 그대로 `skipped`), Cycle 은 `finished`/`blocked`(03 의 대체 Run 이 없으면). 대체는 03 의 버려진 Run 규칙이 아니라 별도: 취소된 run 은 `run.finished` 가 있어 버려진 Run 이 아니므로 자동 대체되지 않는다(사람이 Run 을 다시 등록한다; 후속 후보).

재시도 정책 — 테스트 재시도(2026-11-08, retry-policy 티켓 01, `packages/runner/src/runner.ts`): `runTests` 옵션 `retries`(기본 0, 최대 5)만큼 **failed** 테스트를 다시 돌린다. blocked(기기 문제라 반복해도 같다)·skipped 는 재시도하지 않는다. 시도마다 새 `attemptId` 로 `attempt.started(attemptNo n)` → … → `attempt.finished` 를 보고하고, 실패 시도의 아티팩트는 그 attemptId 로 남으며, 시도 사이에는 실패 직후의 `session.restart` 로 앱 상태를 버린 뒤 `open` 으로 다시 시작한다. `TestResult.result`·`durationMs` 는 마지막 시도 기준, `attempts` 는 돈 시도 수, 앞선 시도의 경고는 `시도 n:` 접두어로 합쳐지며 `RunReport.summary` 는 마지막 결과 기준이다. 러너는 "flaky" 를 모른다 — Verdict 가 attemptNo 최대 Attempt 와 이전 실패로 `passed-flaky` 를 만든다. fixture 에 `attemptNo` 가 있어 검증용 샘플이 "첫 시도만 실패" 를 만들 수 있다(제품 테스트가 분기하는 용도는 아니다). 횟수는 에이전트 `--retries`/`SINCLAIR_AGENT_RETRIES` 로 주되 데몬은 Cycle 의 `suite.retries`(`POST /cycles`, 정수 0~5) 가 있으면 그것을 우선한다(QA 담당자가 Cycle 단위로 정책을 고른다). 상한 5 는 러너·control-plane·runner-agent 에 각각 상수로 있고 apps 가 러너를 import 하지 않으므로 러너 테스트가 같은 숫자임을 확인한다.

재시도 정책 — 버려진 Run(2026-11-08, retry-policy 티켓 03, `apps/control-plane/src/cycle-view.ts` `sweepAbandoned`): 클레임돼 lease 를 가진 Run 에 이벤트가 있는데 `run.finished` 가 없고 lease 가 만료된 지 유예 이상 지나면 **버려진 Run** 이다. lease 없이 보고되는 Run(`run --run` 처럼 에이전트가 스스로 등록·실행)은 대상이 아니다: 서버는 이벤트의 생산 시각 `at` 만 알아 스풀이 늦게 비워지는 정상 상황을 죽음으로 오판할 수 있어, 그런 Run 은 그 에이전트가 끝까지 책임진다. 유예는 lease TTL 과 같다(기본 60초; heartbeat 를 두 번 놓치고 TTL 이 지난 뒤 한 번 더 기다려 네트워크 흔들림과 진짜 죽음을 가른다). 판정은 별도 스케줄러 없이 `POST /runs/claim`(모든 Cycle)과 `GET /cycles/:id`(그 Cycle) 때 한다. 정리는 합성 `run.finished state=infra-failed` 를 `eventId = abandoned:<runId>` 로 Ingest 에 넣는 것이라 멱등이고(두 서버·두 번 호출에도 하나), 투영이 `infra-failed` 가 되어 남은 케이스는 `blocked` 다. Cycle 의 `retryLimit`(POST /cycles, 정수 0~5, 기본 1, 타깃별 대체 횟수) 안이면 같은 타깃의 **대체 Run**(`RunRegistration.replaces`) 을 등록하고 원래 Run 에 `replacedBy`/`abandonedAt` 을 표시한다. 대체 Run id 는 결정적(`retry:<runId>`)이라 두 서버가 동시에 정리해도 등록은 한 번만 성공하고, 등록 뒤 표시 전에 죽어도 다음 정리가 같은 id 로 표시를 마친다. 후보 검사는 레코드(lease)만으로 하고 만료된 lease 가 있을 때만 이벤트를 읽으므로 Cycle 이 쌓여도 클레임 비용은 레코드 조회뿐이다. Verdict 는 `replacedBy` 가 있는 Run 을 상태·매트릭스·"모든 Run finished" 판정에서 빼고 대체 Run 을 본다(행에는 이력으로 남는다). 대체 Run 이 또 버려지면 한도 안에서 반복하고, 한도를 넘으면 `infra-failed` 로 남아 Cycle 은 `blocked`. `GET /cycles/:id` 는 run 행의 `replaces`/`replacedBy`/`abandonedAt` 과 Cycle 의 `retryLimit`, 타깃별 `retriesUsed` 를 준다. 서버 옵션 `--lease-ttl-ms`/`SINCLAIR_CP_LEASE_TTL_MS` 가 TTL 과 유예를 함께 바꾼다. 이벤트가 전혀 없는 Run 의 lease 만료 재클레임은 그대로 "Run 클레임" 규칙이다. 대체된 Run 의 heartbeat 는 lease 소유자여도 `409 code: replaced`(lease 를 연장하지 않음): 끊겼다 돌아온 원래 에이전트가 이걸 lease 상실로 받아 취소해야 두 Run 이 같은 몫을 계속 보고하지 않는다(retry-policy 04 에서 발견). 이 경우 원래 Run 의 저장된 상태는 합성 종료의 `infra-failed` 다: 투영은 `run.finished` 가 여럿이면 `at` 이 가장 이른 것을 쓰고(도착 순서와 무관), 에이전트의 `cancelled` 보고는 그보다 뒤 시각이라 저장되지만 상태를 바꾸지 않는다. 종단 증명은 `verify-runner-agent` 의 `retry-e2e.sh`(강제 종료·한도 초과·lease 상실 세 경로).
